# План интеграции проверок веб-сервисов

## 1. Цель и границы проекта

Развить существующий PE-сканер в локальную платформу для проверки собственных приложений:

1. PE-файлы и ZIP-архивы — существующее направление.
2. Веб-приложения и API — новое направление для анализа HTTP(S), конфигурации и ограниченного DAST.
3. Нагрузочные проверки — отдельный режим с отдельными лимитами и отчётом.

Результат сканирования — перечень проверенных контролей, найденных проблем, доказательств и рекомендаций. Он не является гарантией безопасности и не заменяет анализ кода, проверку конфигурации инфраструктуры и ручную проверку бизнес-логики.

Приложение сейчас запускается на Windows как ASP.NET Core сервер с React UI в браузере. Это не нативное Windows-приложение. Нативная оболочка для Windows может быть отдельным этапом после готовности веб-проверок.

## 2. Текущее состояние проекта

- В `Core/Scanning/ScanModels.cs` уже есть `ScanTargetKind.WebApplication`, универсальные `ScanFinding`, `ScanModuleResult` и `ScanReport`.
- `ScanCoordinator` выбирает модули по `IScanModule.Supports(...)`.
- Зарегистрированный сервером `PeScanModule` принимает только `PeFile`.
- API сейчас предоставляет сканирование PE, ZIP и health endpoint.
- UI (`UI/src/App.tsx`) работает с файлами и архивами; формы для URL и отчёта веб-скана пока нет.
- В `UI/vite.config.ts` настроен локальный прокси к API на `http://localhost:5290`.

Следовательно, поддержка `WebApplication` в общей модели пока является заделом, а не работающей возможностью.

## 3. Рекомендуемые профили сканирования

| Профиль | Назначение | Поведение |
|---|---|---|
| **Passive baseline** | Первый безопасный MVP | Получает ограниченный набор страниц, не внедряет тестовые значения и не отправляет изменяющие данные запросы. Проверяет TLS/HTTP, заголовки, cookies, ошибки и доступные метаданные. |
| **API review** | Проверка API | Использует предоставленную OpenAPI-спецификацию и проверяет доступность, схему, коды ответа, ошибки и базовые признаки проблем с авторизацией. |
| **Limited active** | Поиск типовых уязвимостей на тестовой среде | Отправляет ограниченные безвредные проверки. Требует отдельного включения, заданного scope и низких лимитов. Пропускает изменяющие запросы по умолчанию. |
| **Performance** | Проверка отклика и предельной нагрузки | Отдельный инструмент/процесс с явными профилем нагрузки, порогами и разрешённой целью. Не запускается обычной кнопкой «Сканировать». |

Первый выпуск должен реализовать только Passive baseline. Каждый последующий профиль включается после прохождения тестов предыдущего этапа.

## 4. Архитектура интеграции

### Core

- Добавить `WebScanModule : IScanModule` и реализовать `Supports(ScanTargetKind.WebApplication)`.
- Не помещать настройки скана, OpenAPI-документ и учётные данные в строку `ScanTarget.Value`. Добавить отдельную модель запроса/контекста веб-проверки.
- Разделить правила по группам, например `WEB-TLS`, `WEB-HEADERS`, `WEB-COOKIE`, `WEB-ERROR`, `WEB-API`, `WEB-AUTH`.
- Использовать текущие `ScanFinding`, `ScanArtifact` и `ScanModuleResult`; не вводить второй независимый формат findings.
- Для каждого правила хранить severity, confidence, описание, доказательство, рекомендацию и ссылку на версионированный контроль ASVS/WSTG.
- Добавить понятия `NotRun`, `Skipped`, `Passed` и `NeedsReview` для статуса отдельной проверки: отсутствие finding не всегда означает, что контроль проверен.

### Server

Добавить:

- `WebScanService` — orchestration, scope, таймауты, лимиты запросов и отмена.
- `WebScannerOptions` — allowlist хостов/портов, лимиты, глубина обхода, разрешённые профили.
- DTO запроса и ответа для URL/API-скана.
- Endpoint `POST /api/scan/web` для короткого passive-скана.
- Для длительных active/performance задач позднее добавить очередь заданий: `POST` возвращает `scanId`, `GET /api/scan/{scanId}` возвращает статус и результат, `DELETE /api/scan/{scanId}` отменяет задание.

Заголовки авторизации не должны попадать в логи, ответы, артефакты, исключения или историю сканов. Не сохранять их на диск.

### UI

Расширить текущий React интерфейс разделами:

- **PE-файл** — существующий upload.
- **Веб-сервис** — URL, профиль, scope и запуск passive baseline.
- **API** — загрузка OpenAPI-файла или адрес спецификации в пределах разрешённой цели.
- **Нагрузка** — отдельная форма и отдельное подтверждение; добавить только после отдельного этапа.

В интерфейсе показывать проверенную цель, время, профиль, покрытие, лимиты, findings, skipped checks, evidence и рекомендации. У активного профиля показывать точное предупреждение о том, какие запросы будут отправлены.

## 5. Защита самого сканера

Сканер, принимающий URL, может стать SSRF-прокси. Защита scope обязательна до отправки первого HTTP-запроса.

1. Разрешать только `http` и `https`; отклонять URL с userinfo, неизвестной схемой и некорректным портом.
2. Сверять hostname и порт с серверным allowlist. Для локальной разработки разрешать только loopback по явной dev-настройке.
3. По умолчанию запрещать адреса loopback, private, link-local, multicast и cloud metadata. Исключение — локальные цели в dev-режиме с явным разрешением.
4. Проверять DNS-результаты перед соединением и повторно при редиректах; редирект разрешать только внутри того же scope. Не позволять DNS rebinding обходить проверку.
5. Ограничивать число редиректов, время соединения/ответа, общий бюджет запросов, параллелизм и максимальный размер ответа.
6. Ограничить обход страниц same-origin; отключить robots.txt как механизм безопасности, считать его только подсказкой.
7. Не использовать запросы к произвольным внешним callback/OAST-службам.
8. Passive baseline ограничить безопасными методами `GET`, `HEAD`, `OPTIONS`. Active проверки не должны отправлять `POST`, `PUT`, `PATCH`, `DELETE` или формы без отдельной реализации и явного разрешения.
9. Настроить политику обработки cookies, токенов и редактирования секретов; не сохранять тело ответа целиком без необходимости.
10. Учитывать, что даже `GET` может менять данные в плохо реализованном приложении. Активные проверки проводить на staging-копии.

Начальные ограничения MVP следует сделать консервативными и конфигурируемыми: небольшая глубина обхода, низкий темп запросов, ограниченное число страниц и короткий общий timeout. Конкретные значения фиксируются после измерений на локальной тестовой цели.

## 6. Этапы реализации и критерии готовности

### Этап 0 — уточнить продуктовую область

- Зафиксировать, что основной сценарий — локальная проверка собственных проектов на Windows.
- Разделить в документации PE-сканер, веб-сканер и нагрузочный инструмент.
- Определить формат allowlist и dev-настройку для loopback.
- Утвердить, что целевые проверки запускаются только на своих системах или системах с явным разрешением.

**Готово, когда:** README и UI ясно разделяют три сценария, а текущие PE-возможности остаются неизменными.

### Этап 1 — модели и безопасность цели

- Расширить типизированные модели веб-цели и профиля сканирования.
- Реализовать URL parsing, allowlist, DNS/IP-фильтрацию, правила редиректов и лимитирование запросов.
- Добавить unit-тесты на loopback, private/link-local/metadata адреса, IPv4/IPv6, смену DNS-ответа, редиректы и обход allowlist.
- Добавить cancellation token для всех сетевых операций.

**Готово, когда:** сканер не отправляет запрос к запрещённой цели даже при редиректе или подмене DNS; тесты подтверждают границы.

### Этап 2 — Passive baseline

- Создать `WebScanModule` и зарегистрировать его рядом с `PeScanModule`.
- Проверять доступность HTTPS, валидность/срок сертификата, редиректы, безопасные заголовки и атрибуты cookies.
- Проверять утечки типовых диагностических страниц и избыточных серверных заголовков без перебора путей.
- Ограниченно обходить same-origin ссылки, не отправляя формы и не создавая состояние.
- Добавить severity/confidence и статус покрытия каждой проверки.

**Готово, когда:** локальная безопасная fixture-система выдаёт ожидаемые findings; скан пустой безопасной цели показывает, что было проверено и что не проверялось.

### Этап 3 — API и OpenAPI

- Принимать OpenAPI 3.x файл или URL из уже разрешённого scope.
- Проверять соответствие ответов схемам, документированные и фактические маршруты, коды ошибок и базовые требования к авторизации.
- Не генерировать автоматически запросы, которые меняют состояние или удаляют данные.
- Добавить ограничение размера/сложности спецификации и защиту от ссылок `$ref` на внешние или запрещённые ресурсы.

**Готово, когда:** контракты тестируются на демонстрационном API; внешние `$ref` не позволяют читать локальные файлы или обращаться к запрещённым адресам.

### Этап 4 — ручная проверка входа и ограничений

- Добавить безопасный сценарий проверки throttling/lockout на выделенной тестовой учётной записи.
- Не использовать списки паролей и не выполнять массовый перебор. Пользователь задаёт тестовый аккаунт и малое число контролируемых неудачных попыток.
- Измерять ответы `429`, задержки и наличие временной блокировки; предупреждать о возможной блокировке тестового аккаунта.
- Проверять ролевой доступ с двумя тестовыми ролями только при наличии явно предоставленных учётных данных.

**Готово, когда:** проверка ограничена тестовой целью и аккаунтом, секреты не сохраняются, а любой отказ/превышение лимита корректно останавливает сценарий.

### Этап 5 — ограниченные активные проверки

- Ввести отдельный профиль `Limited active`; он выключен по умолчанию.
- Разрешить только небольшой набор неразрушающих правил с безопасными маркерами и малым числом запросов.
- Исключить destructive payloads, реальные команды ОС, запись файлов, удаление объектов, массовое создание данных и внешние OAST callbacks.
- Ограничить правила по методам, маршрутам, числу запросов, темпу и времени; предусмотреть немедленную отмену.
- Рассмотреть интеграцию OWASP ZAP как отдельного движка через адаптер, а не перенос всего набора атак в сам Core. Вызов active scan должен работать только в тестовом окружении и в заданном scope.

**Готово, когда:** тесты подтверждают request budget, scope, cancellation и отсутствие запросов к внешним/запрещённым адресам; UI заранее показывает профиль и его последствия.

### Этап 6 — нагрузка и устойчивость

- Держать нагрузочный генератор отдельно от обычного security scan. Начальный вариант — документированные шаблоны сценариев для k6 и импорт результатов в отчёт.
- Для сценария задавать ramp-up, стабильную фазу, ramp-down, максимум виртуальных пользователей/RPS и продолжительность.
- До запуска требовать staging/локальную цель, allowlist и явно заданный потолок нагрузки.
- Собирать latency p50/p95/p99, error rate, throughput и доступные метрики CPU, памяти, пула соединений и базы данных.
- Добавить пороги pass/fail и автоматическую остановку при росте ошибок, превышении времени ответа или недоступности сервиса.
- Не выполнять стресс- и spike-тесты на production из UI MVP.

**Готово, когда:** тест постепенно увеличивает нагрузку, останавливается на заданном лимите, формирует воспроизводимый отчёт и не стартует без заданной цели и максимального профиля.

### Этап 7 — отчёты, история и качество

- Добавить экспорт JSON/HTML с версией правил, профилем, покрытием, временем и scope.
- Секреты и персональные данные редактировать до экспорта.
- Для каждого finding указывать confidence и путь проверки; ручное подтверждение должно отличаться от автоматического сигнала.
- Добавить regression tests на локальном наборе уязвимых и исправленных demo-endpoints.
- Добавить integration tests API, UI smoke checks и CI build/test.
- В документации дать remediation-first инструкции; результат сканера не должен обещать «сервер защищён» только потому, что findings отсутствуют.

**Готово, когда:** отчёты воспроизводимы, покрытие проверок видно, регрессии обнаруживаются CI, а успешный отчёт явно показывает ограничения проверки.

## 7. Организация тестовой среды

Создать отдельный локальный проект `TestWebTarget` с безопасными демонстрационными endpoints:

- корректные и некорректные security headers;
- cookies с разными атрибутами;
- публичный и защищённый маршрут;
- controlled rate-limit на тестовом логине;
- endpoint для валидации схемы и обработки ошибок;
- параметризованный запрос и намеренно небезопасный SQL-fixture только на изолированной тестовой базе.

Никакие тестовые уязвимости не размещать в публичной сети. Интеграционные тесты должны проверять и детектирование, и отсутствие нежелательных сетевых запросов.

## 8. Предлагаемая структура файлов

```text
Core/
  Web/Models/       WebTarget, WebScanProfile, WebScanContext
  Web/Http/         ограниченный HTTP transport, scope policy
  Web/Rules/        passive checks и позже limited active checks
  Modules/          WebScanModule
Server/
  Options/          WebScannerOptions
  Services/         WebScanService, ScopeValidator
  DTOs/             WebScanRequest, WebScanResponse
Test/
  Web/              unit tests и локальные test targets
UI/src/
  components/       TargetForm, ProfileSelector, WebReportView
  hooks/            useWebScan
```

Названия можно подстроить под фактическую структуру, но сетевые правила и scope policy должны оставаться в Core/отдельном сервисном слое, а не в React-компонентах.

## 9. Стандарты и ориентиры

- [OWASP Web Security Testing Guide](https://owasp.org/projects/web-security-testing-guide?tab=main) — методика и сценарии тестирования; стабильная версия проекта сейчас 4.2, 5.0 разрабатывается.
- [OWASP SQL Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet) — базовые меры против SQL-инъекций.
- [OWASP ZAP Passive Scanner](https://www.zaproxy.org/docs/desktop/addons/passive-scanner/) — пример безопасного пассивного анализа трафика.
- [Grafana k6 thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/) — формализация порогов производительности.

## 10. Текущее состояние реализации

По состоянию на 2026-11-05:

- **Готово:** `WebScanModule`, пассивная same-origin проверка, ограничение страниц/запросов/размера ответа, точный allowlist origin, проверка адреса при фактическом соединении, отключённые proxy/auto-redirect, отказ от перехода за scope.
- **Готово:** findings по HTTP, базовым security headers, cookies и раскрывающим заголовкам; evidence не содержит значений cookies.
- **Готово:** локальный OpenAPI 3.x JSON обзор с лимитом 1 MiB; внешние `$ref` не загружаются, mutating endpoints не вызываются. В opt-in режиме выполняется ограниченное число GET к документированным маршрутам без credentials, проверяются заявленные коды ответа и базовая часть JSON Schema (`type`, `required`, `properties`, `items`, `enum`, локальные `$ref`); отмечается неожиданный 2xx у документированной защищённой операции. Это частичная runtime-валидация контракта, не полный валидатор OpenAPI/JSON Schema.
- **Готово:** ограниченные active GET сигналы для ошибок БД и сырого отражения инертного HTML-маркера; они помечаются как сигналы, не как доказательство exploitable SQLi/XSS.
- **Готово:** отдельная bounded-проверка login throttling: только выделенная тестовая учётная запись, до пяти попыток с случайными паролями, HTTPS для удалённой цели, явное подтверждение в UI.
- **Готово:** отдельный генератор ограниченного k6 GET-сценария и импорт JSON summary; приложение не запускает нагрузочный генератор.
- **Остаётся:** полноценные DAST-проверки SQL injection/XSS и опциональный адаптер ZAP, тестирование ролевой авторизации, полный валидатор OpenAPI/JSON Schema и дополнительные интеграционные тесты API/кроссплатформенности. Общий веб-отчёт можно скачать как JSON. Проверка DNS pinning, private/metadata адресов, same-origin redirect, opt-in active budget и обнаружения несоответствия объявленной схеме покрыта отдельными unit-тестами.

Эти функции не означают, что веб-сканер является полноценным penetration-testing продуктом. Отчёт должен сохранять ограничения покрытия и требовать ручной верификации находок.

## 11. Рекомендуемый порядок дальнейших работ

Основной сквозной сценарий уже реализован: UI → локальный API → ограниченный сканер → JSON-отчёт. Следующий этап — заменить unit-fixtures на отдельный локальный `TestWebTarget` и добавить API/UI integration tests в CI. Затем можно расширять валидатор OpenAPI и добавлять новые DAST-правила по одному, каждое с тестами безопасности scope и request budget. Адаптер ZAP остаётся отдельной будущей работой для staging. Полноценный DAST нельзя обозначать как завершённый, пока нет изоляции, аудита каждого запроса и тестов границ.
